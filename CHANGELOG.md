# Changelog

## 2.17.0
- **Full output on click**: click the message under a repository (Repositories page or hub panel) and a window opens with everything the last action printed, as in a console: `git pull`, each step of Update (`$ command` and its output), install output, a command's output. *Copy all* copies it. Works for successful results too. (Notifications are not clickable; the row keeps the text until the next action.)
- **Update closes the tool when the plain `git pull` was all you had**: Update only offered itself when DevPilot found a tool by path or an install step, so a tool started through a shortcut or launcher was never closed. The gear now lists every tool of the hub: tick the ones to close and start again (tools found by path are shown ticked and locked), and tools whose arguments name the repository are found too. The row summary says "no tool linked" when none is.
- **DevPilot updates itself**: Update on the DevPilot repository pulls, then closes DevPilot, runs `scripts\install.cmd` in a window of its own (kept open on failure), and the new version starts by itself; start-with-Windows is kept as it was. Nothing happens when already up to date.
- Core: `RepoPullResult.Output / Transcript`, `RepoCommandResult.FullOutput / Transcript`, `RepoOutput`; `RepoConfig.ToolIds`; `RepoUpdatePlan.SelfUpdate`, `RepoUpdatePlanner.SelfUpdateCommand / IsAutoMatch`; `RepoSyncService.SelfUpdateRequested / AutostartProbe`. Tests: `RepoUpdateTests` (self update, linked tools, arguments match, full output).

## 2.16.0
- **Version of each repository**: the Repositories page and the hub panel show the version of every clone next to its branch (hover: which file it came from and the commit). Read from the files only, nothing is run: `devpilot.tool.json`, `Directory.Build.props` / csproj `<Version>` (app project first), `pyproject.toml`, Python `__version__` / `VERSION` (`version.py` or a package `__init__.py`, also under `src\`), `package.json`, `VERSION` / `version.txt`; otherwise the short commit.
- **Old → new after Pull and Update**: the result line and the notification read "2.14.0 → 2.15.0 · 3 files changed…", or "2.15.0 (unchanged)" when the pull did not change the version; *Already up to date* and *Reinstall now* name the current version. It is the version in the clone, not of the running program.
- Core: `RepoVersion` (reader, short commit from the `.git` files incl. packed refs and worktrees, change text), `RepoVersionInfo`; `RepoPullResult.Before / After / VersionChange`; `RepoScanner.GitDir`. Tests: `RepoVersionTests` (each source and its order, MSBuild property refs ignored, commit fallback, packed refs, detached HEAD, change text, pull with a fake git, real git round trip with a version bump).

## 2.15.0
- **Update** on a repository (the row button in the hub panel and on the Repositories page): `git pull`, and when something new came, **close the running tools of that repository, run its install step, and start them again**. Nothing is closed or installed when the repository is already up to date; a repository with uncommitted changes is skipped; after a failed install the tools stay closed and the result says so (with the last lines of the install output). The row shows each step ("Update: closing ScreenPilot…").
- **Automatic preset, different for each kind of project**: *Python* uses the repository's install script (`Install.bat`, `install.cmd`, `scripts\install.cmd`, `.ps1`), else `pip install -r requirements.txt` in its `.venv`; *C#* uses the install script if there is one, else `dotnet build <solution or project> -c Release`. Which tools to close: the process-type tools DevPilot manages that start a program from inside the repository. Only tools that were running are started again.
- Per repository (gear on the row): switch Update off, switch closing/starting the tools off, type your own install command (empty = automatic), *Reinstall now* (the same without the pull), and when the plain *git pull* button is also shown (Automatic = only when there is no Update). The editor shows what Update will do for that repository.
- DevPilot's own repository is never updated from inside DevPilot (the running program would be replaced): close it and run `scripts\install.cmd`.
- Fix: stopping a tool on purpose (Stop in the hub, or an update) no longer makes the monitor start it again through auto-restart.
- Core: `RepoUpdatePlanner`, `RepoAction` kinds (pull / update / command), `IToolControl`; `RepoSyncService.UpdateAsync`; `ToolControl`. Settings: `Repos.Items[].Pull / UpdateEnabled / InstallCommand / RestartTools` (replaces `IncludePull` from 2.14.0). Tests: `RepoUpdateTests` (detection, scripts, dotnet build, venv pip, tool matching, actions, and the update flow with fakes: order, up to date, local changes, failed install, only running tools, restart off, tool that does not start, reinstall).

## 2.14.0
- Hub: the sync button in the header now opens a **repositories panel** (it stays open until you close it with X or Esc): every repository with a tick, *Pull selected*, a coloured dot and the result for each repository as it finishes, and one button per row. Tray menu: *Repositories…* opens the same panel; *Pull repositories* still pulls the ticked ones at once.
- **Commands per repository** (Repositories page > the gear on a row): add commands with a name and a command line (for example `dotnet build -c Release` or `Install.bat`), run through `cmd.exe` in the repository folder. *In a window* off (default): runs hidden, the end of the output is shown on the row and a notification says done or failed (exit code and last line); stops after 10 minutes. *In a window* on: opens a console that stays open (`cmd /k`), so an error can be read. A command never waits for keyboard input (hidden mode closes its input). *Offer git pull for this repository* can be switched off.
- **One button, several actions**: the row button runs the only action directly (its label says which: *Pull* or the command name). With a pull plus commands, or several commands, it opens a menu with one button per action.
- A command and a pull never run on the same repository at once: a pull of all skips a repository that runs a command ("Skipped: command running"), and a command is refused while a pull of all runs.
- Core: `RepoConfigs` (actions per repository, repair of the settings), `RepoCommandRunner` (cmd.exe arguments, result, output tail), `ICommandRunner`; Infrastructure: `ShellCommandRunner`; `RepoSyncService.RunCommandAsync`. Settings: `Repos.Items` in config.json. Tests: `RepoCommandTests` (actions, repair, round trip, outcomes, busy handling with fakes, and real `cmd.exe`: output, exit code, working folder, no wait for input, timeout).

## 2.13.0
- New **Repositories** page and *Pull repositories* (hub header button, tray menu): choose the folder that holds your clones once; DevPilot finds the git repositories in it (3 levels deep, not inside a repository, not in `node_modules`/`bin`/`obj`/virtual environments) and lists them with their branch. Tick the ones to pull (new clones are ticked automatically), then pull them all, or one with its own *Pull* button.
- Safe by design: a repository with uncommitted changes to tracked files is skipped; the pull is `git pull --ff-only`, so DevPilot never merges, rebases or stashes. Repositories are pulled one after another. git runs hidden, with English output and terminal prompts off (a missing sign-in fails instead of hanging). Each repository shows its result: updated (with the change line), up to date, skipped (local changes / no upstream / diverged), not trusted by git (dubious ownership, with the command to fix it), sign-in failed, remote unreachable, git not found, timed out.
- Automatic pull (off by default): once when DevPilot starts, or at start and every N minutes (5–1440); optionally notify only when something changed or needs attention. Not run in the CI smoke test.
- Core: `Core/Repos/RepoScanner`, `Core/Repos/RepoPull`, `IGitRunner`; Infrastructure: `GitRunner`, `RepoSyncService`; settings: `Repos` in config.json. Tests: `RepoPullTests` (scanner, output classification, safety rules with a fake git, and a real git round trip: update, skip on local changes, refuse to merge diverged branches, no upstream). Docs: `docs/REPOS.md`, `TESTING.md`.

## 2.12.0
- Egress Guard: incident reports. A connection outside the allowlist now writes a plain-text report to `%LOCALAPPDATA%\DevPilot\incidents\` (tool, start path, processes, destination, verdict and why, allowlist in force, recent events, what to do). In `block` mode the tool is stopped *and marked Blocked* (auto-restart no longer restarts it) and a dialog offers to open the report; in `monitor` mode only a notification. Core: `GuardIncident`, `IncidentReport`; `EgressMonitorService.IncidentRecorded` replaces `NotificationRequested`.
- Deny terms: `*` matches up to 40 characters (`project*alpha`), `re:` starts a regular expression; plain terms are unchanged. Used by the scanner, the pre-flight check and `scripts/check-secrets.ps1`. Broken patterns are counted (`LocalPolicy.InvalidTermCount`), never shown. Tests: `DenyTermAndIncidentTests`. Built and tested from a local copy (307 tests pass); not run on a live tool yet.

## 2.11.0
- Egress Guard, step 11 of 11: docs (`docs/GUARD.md`, `network` block in `docs/INTEGRATION.md`) and version 2.11.0. The Guard is new in this release: modes off / monitor (default) / block, scan, approval and drift, runtime monitor, soft offline, kill switch, pre-flight check, repo secret check. Details per step below. Untested on a real Windows desktop; see `docs/GUARD.md` for limits.
- Egress Guard, step 10 of 11 (repo hygiene): `backups/` is git-ignored; CI runs `scripts/check-secrets.ps1` (generic secret patterns in tracked files, same shapes as the scanner's `secret` rule; Guard rules and tests are excluded). The same script runs as a pre-commit hook (`scripts\install-hooks.cmd`, staged files only) and, when `%APPDATA%\DevPilot\policy.local.json` exists, also checks its deny terms; a match reports the file only, never the term. Not run locally; CI pending.
- Egress Guard, step 9 of 11: pre-flight text check. Tray menu > *Check clipboard before pasting into AI* and *Check a file before pasting into AI…* look for terms from the local deny-list and for common secrets and personal data (private keys, access keys, passwords and tokens in assignments, e-mail addresses, IBANs and payment card numbers that pass their checksum, international phone numbers). The result shows only the category, line and column of each hit and never the matched text. Files up to 2 MB. It is a safety net, not a guarantee. Logic in `Core/Guard/TextPreflight`; tests: `TextPreflightTests`. Not run locally; CI pending.
- Egress Guard, step 8 of 11: new **Egress Guard** page in the main window (sidebar, after Monitor). Mode selector (off / monitor / block) with what each does, *Pause / Resume external access*, local-policy status (found / unreadable, never its content), and per tool: status (Not reviewed / Approved / Blocked / Changed since approval), *Scan* (findings with severity, rule, file:line, why and how to fix), *Approve* (stores the current files, git remote and the allowlist you edit here: hosts one per line, ports, *needs no external access*), *Block*, *Reset*, and a *Start offline (soft)* switch. *Scan all* and *Export report* (JSON with rule ids, files, line numbers and counts only; no messages, so no deny-list term or secret can appear). *Recent events* lists connections outside an allowlist or from tools with none (kept in memory only). Core: `AllowlistText`, `GuardReportExporter`. Tests: `GuardTextsTests`. Not run locally; CI (with the UI smoke test of every page) pending.
- Egress Guard, step 7 of 11: kill switch. Tray menu > *Pause external access* / *Resume external access* (`KillSwitchService`): pausing stops the running tools that could use the network and makes the launcher refuse to start them (any guard mode, including off) until you resume; a tool whose allowlist says `allowNone` and non-process entries (folders, URLs) are left alone. The state is saved in the config (`Guard.Paused`), so it survives a restart. `GuardManifest.Network` reads the manifest's `network` block in one place. Tests: `KillSwitchTests`. Not run locally; CI pending.
- Egress Guard, step 6 of 11: soft offline mode. A tool with `GuardOffline` starts with `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` pointing at `http://127.0.0.1:9` (nothing listens there), an empty `NO_PROXY` and `DEVPILOT_OFFLINE=1`; the tool's own extra environment can still override. It only affects tools that honour proxy variables, so it is not a security boundary. No switch in the UI yet (step 8). Tests: `SoftOfflineTests`. Not run locally; CI pending.
- Egress Guard, step 5 of 11: runtime monitor. `EgressMonitorService` polls the TCP connection table (IP Helper API: no packet capture, no driver, no admin rights; TCP only because UDP has no remote endpoint) every 5 s for the processes DevPilot manages and their children, and compares each new connection with the tool's allowlist (what was approved, else the `network` block of `devpilot.tool.json`; declared hosts also match by forward-resolved IP). `monitor`: log + a rate-limited notification (once per tool/host/port per 10 min) for a connection outside the allowlist; `block`: the tool's process tree is stopped; a tool with no declared allowlist is only logged in every mode. Loopback is ignored; `alwaysAllowedHosts` of the local policy applies to all tools. Recent events are kept in memory (`GuardEventLog`) for the Guard page. Tests: new `RuntimeGuardTests` (includes a live TCP-table check). Not run locally; CI pending.
- Egress Guard, step 4 of 11: approval gate. A tool is Unreviewed, Approved, Blocked or Drifted (`Core/Guard/ApprovalGate`, state stored per tool in the config). New setting `Guard.Mode` (`off` / `monitor` default / `block`). The launcher now asks `IGuardGate` before starting a tool that runs a process: in `block` mode only an Approved tool with unchanged files and git remote starts, in `monitor` everything starts and the log notes a warning, `off` checks nothing. Tools in shared folders (drive root, Windows, Program Files) are identified by their program file only, so a start never hashes a whole folder; files over 64 MB are identified by size. The check runs off the UI thread and fails open in monitor mode. No UI yet (page comes in step 8). `EgressMode` moved to `DevPilot.Models`. Tests: new `ApprovalGateTests`. Not run locally; CI pending.
- Egress Guard, step 3 of 11 (internal): `Core/Guard/Provenance` reads the git remote (credentials stripped) and commit from the `.git` files without git.exe, and hashes a tool's files (SHA-256 manifest, skipping `.git`, `bin`, `obj`, `node_modules`…, 5000 files max). `GuardApprovals` creates an approval (stored per tool in the config as `GuardApproval`: digest, remote, commit, date, mode, allowlist) and `CheckDrift` reports NotApproved / Unchanged / Changed when files or the remote differ. Tests: new `ProvenanceTests`. Not run locally; CI pending.
- Egress Guard, step 2 of 11 (internal): `Core/Guard/ToolScanner` scans a tool folder (C#, Python, JS/TS, PowerShell, batch, config; skips `bin`, `obj`, `node_modules`, `.git`; 3000 files, 512 KB per file) for HTTP/socket/FTP/SMTP clients, hard-coded URLs and IPs, telemetry, auto-update, uploads, clipboard/screen/key capture, process spawning, persistence, AI clients, embedded secrets and local deny-list terms. Rules are JSON data (`GuardRuleSet`), each with a short why and fix. Findings never contain the matched text. Tests: new `ToolScannerTests`. Not run locally; CI pending.
- Egress Guard, step 1 of 11 (internal, no visible change): Core/Guard model (`EgressMode`, `GuardFinding`, `GuardReport`), `ToolNetworkPolicy` for an optional `network` block in `devpilot.tool.json` (hosts with `*.` wildcard, ports, `allowNone`), and `LocalPolicy` read from `%APPDATA%\DevPilot\policy.local.json` (optional, never logged). Tests: new `GuardModelTests`. Not run locally (no .NET SDK in the authoring environment); CI result pending.

## 2.9.0
- Tools & groups > Add > *From a project folder…*: pick a cloned repository and DevPilot works out how to start it. It recognises a `devpilot.tool.json`, a Python package (`python -m`, also under `src`) or script (using the project's `.venv` when present), a C# program (the built `.exe`, else `dotnet run`), a Node app (`npm start`), a launcher script (`start`/`run` `.cmd`/`.bat`/`.ps1`) or a single `.exe`; a known tool (ScreenPilot…) also gets its preset. Anything else is added as a folder. The scan only reads names, 3 levels deep, skips `.git`, `node_modules`, `bin`-like and virtual-environment folders and stops after 1500 entries, so large solutions stay fast. Logic in `DevPilot.Core/Detection/ProjectScanner.cs`.
- Tests: new `ProjectScannerTests`. Not run locally (no .NET SDK in the authoring environment); CI result pending.
